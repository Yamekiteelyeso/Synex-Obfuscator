# Synex Luau Next — threat model vs. Voltfuscator 7.8

This comparison treats the Voltfuscator characteristics below as claims supplied in the project brief, not as an independent audit of its implementation.

| Area | Voltfuscator 7.8 (brief) | Synex Luau Next foundation | Current limitation |
|---|---|---|---|
| Stream cipher | ChaCha20 | XChaCha20 stream cipher | Authentication is HMAC-SHA-256, not Poly1305 AEAD |
| Key separation | One runtime-derived key | HMAC-derived encryption and integrity keys per prototype salt | Master keys must be provisioned outside an untrusted client for real secrecy |
| Nonces | Session nonce | 24-byte nonce per record; compiler rejects reuse within one prototype | Nonces must be generated by a trusted CSPRNG/build service |
| Constant/record integrity | Debug-derived anti-tamper and instruction chain | HMAC chain over ciphertext, AAD, position and previous record | Embedded MAC key can be extracted; no remote trust anchor |
| Runtime state | Debug function metadata | Local digest over PC, SP, previous operand, steps and opcode | Digest is telemetry, not proof of valid state on an attacker-controlled process |
| Dispatch | Binary search tree | Handler table in the modular VM; existing production emitter has randomized dispatcher arms | Modular VM is not yet integrated into the production emitter |
| Bytecode representation | Base-45 stream | Fixed-width 20-byte records encrypted independently | No base-45 framing/compact binary packer yet |
| Environment probing | Executor/Roblox environment probes | Optional capability detection; no executor global is required | No claim that spoofed client environments can be trusted |
| Memory handling | Lazy string decoding | Decrypt one record at a time; no complete plaintext bytecode array | Luau strings are immutable; physical zeroization cannot be guaranteed |
| Build polymorphism | Randomized wrapper | Deterministic opcode/salt plan from explicit seed | Full emitter-level build polymorphism remains in existing TypeScript emitter |
| Error surface | Native-looking errors | Generic Luau-style errors in the modular reader | Exact native stacktrace parity has not been verified |
| Compatibility | Synapse, Script-Ware, Wave | Luau CLI CI | Each executor still needs real-device compatibility testing |
| Performance/size | Not independently benchmarked here | No performance claim | 500k instructions/s, <20% integrity overhead and <=3x size remain unverified |

## Trust boundaries

**Protected against:** accidental corruption, basic offline edits that do not also recover the embedded MAC key, record swapping, and reuse of a nonce within one prototype.

**Not protected against:** an attacker who controls the client process, can inspect memory, extracts master keys, replaces the runtime, hooks all relevant primitives before execution, or can execute an equivalent copy of the program.

**Key provisioning:** `VM.deriveKeys` derives separate per-prototype encryption and integrity keys from master keys and the prototype salt. This reduces cross-prototype key reuse, but does not create secrecy if the master keys are shipped in the payload.

**Entropy:** heap addresses, GC counters, scheduler timing, and debug metadata are not cryptographic randomness. They may diversify behavior, but keys and nonces must come from a trusted build system or platform CSPRNG.

## Integration status

The Luau modules and their CI tests are modular foundations. The production emitter in `packages/vm/src/emit.ts` still emits its existing 9-field integer records and has not yet been migrated to this encrypted v1 format. Do not enable this format for user payloads until emitter integration, equivalence tests, tamper tests, and performance benchmarks pass.
